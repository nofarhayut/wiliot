Task 01 / Infrastructure

The AWS foundation, as Terraform modules

Each resource is its own reusable module, composed together in one environments/dev root with remote state in S3. Nothing is clicked in the console.

VPC

modules/network

Network with 2 public + 2 private subnets across two AZs, an internet gateway, one NAT gateway and route tables.

EKS

modules/eks

Managed Kubernetes cluster on 1.31 with a node group of two t3.medium workers.

RDS Postgres

modules/rds

Private PostgreSQL, its own subnet group and security group, and a generated password.

ECR

modules/ecr

Container image repositories with a lifecycle policy to keep only recent images.

IAM

modules/iam

The roles EKS needs — one for the control plane, one for the worker nodes.

All five wired together in
environments/dev/
with a single team = devops tag on every resource.

Considerations

One module per resource

Reusable and easy to read. Dependency order is network / iam / ecr, then eks, then rds.

Security groups sit with what they protect

RDS only accepts port 5432 from the EKS security group, so the database is reachable only from inside the cluster.

The database is private

No public access and encrypted at rest — nothing about it faces the internet.

No passwords in the code

The DB password is generated by Terraform and only lives in encrypted state. Read on demand, never committed.

Remote, locked state

Terraform state lives in an S3 bucket with locking, so applies are safe and shareable.

Cheap by default, ready to scale

One NAT, a small DB, two small nodes — fine for a demo. The network is split from the cluster, so a second cluster can share the VPC later.

Task 02 / Data pipeline

Fake data in, clean rows out — every 15 minutes

Airflow asks Microcks for a batch of fake orders, cleans them in plain Python, and writes them into the RDS orders table. The whole thing is deployed with Helm, one command away.

Microcksmicrocks namespace

A fake API, installed from its official Helm chart. Serves GET /orders and returns ~20 random orders each call. Auth off and a throwaway database — demo settings, noted as such.

Airflowairflow namespace

The orchestrator. Its scheduler runs the job on a timer, the dag-processor reads the DAG file, and the web UI is exposed to the internet through a load balancer.

The DAGdags/ingestion_dag.py

The actual job in three steps — extract (call the mock), transform (clean it), load (write to RDS). Safe to re-run: it never creates duplicates.

RDS connectionkubernetes secret

The database connection string is handed to Airflow as a secret, so the DAG uses it by name (rds_postgres) and no password ever sits in the code.

See it running

A few commands to look at any part of it

Standard kubectl — runnable from any machine with access to the cluster, not tied to a local setup. Point kubectl at the cluster once, then inspect the DAG, the pods, the logs, the mock, and the rows in the database.

kubectl — wiliot-dev
# point kubectl at the cluster (any machine with AWS access)
$ aws eks update-kubeconfig --name wiliot-dev --region us-east-1

# what's running
$ kubectl -n airflow get pods        # api-server, scheduler, dag-processor, db
$ kubectl -n microcks get pods       # microcks, mongodb

# the DAG: is it registered? any parse errors?
$ kubectl -n airflow exec deploy/airflow-scheduler -- airflow dags list
orders_ingestion   dags-folder   ✓ no import errors

# tail the logs of a component
$ kubectl -n airflow logs deploy/airflow-dag-processor -c dag-processor

# open the Airflow UI locally  ->  http://localhost:8080 (admin/admin)
$ kubectl -n airflow port-forward svc/airflow-api-server 8080:8080

# open Microcks and pull a batch of dummy orders
$ kubectl -n microcks port-forward svc/microcks 8585:8080
$ curl -s http://localhost:8585/rest/Orders/1.0.0/orders | jq '.[0]'

# the payoff: rows that landed in RDS
$ kubectl -n airflow exec deploy/airflow-scheduler -- \
    python -c "PostgresHook('rds_postgres').get_first('SELECT count(*) FROM orders')"
count = (40,)
